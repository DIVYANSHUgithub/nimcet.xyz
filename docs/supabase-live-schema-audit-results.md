**Status:** Read-only production audit results recorded  
**Database:** Supabase PostgreSQL 17.6  
**Scope:** Initial findings were supplied from the live audit. A follow-up SELECT-only catalog audit was run through the authenticated Supabase CLI on 2026-11-01 to verify exact PostgreSQL catalog metadata. No database changes were issued.

## Executive summary

The verified production inventory shows one application table in `public`: `questions`, together with its sequence `questions_id_seq`. The table has 15 columns, JSONB `options`, nullable integer `correct_option`, and text `status`. Its constraints and two indexes cover identity, question uniqueness, status, answer-index validity, and JSON-array options. Row-level security (RLS) is enabled, with a public-read policy limited to published questions for `anon` and `authenticated`.

The audit found 102 published questions for NIMCET 2026 across four sections. No drafts, missing answers, or invalid JSON option arrays were reported. The production inventory also includes an RLS helper function and a disabled event trigger; the disabled trigger must not be treated as active automatic RLS enforcement.

This is an audit record, not a migration proposal or authorization to change production. Exact constraints and sequence parameters were verified by the follow-up catalog query. Auth JWT configuration, Storage bucket settings, effective future-object privileges for the migration/runtime roles, and complete migration state remain unverified.

### `public.questions` structure and constraints

- The table has **15 columns**.
- Verified column facts include:
  - `options` is `jsonb`.
  - `correct_option` is nullable `integer`.
  - `status` is `text`.
- Reported constraints include:
  - a primary key;
  - a unique exam/year/section/question-number constraint;
  - a status check;
  - a correct-option check; and
  - a JSON-array options check.
- Two indexes exist: the primary-key index and the unique exam/year/section/question-number index.

The follow-up catalog query verified these exact definitions:

| Constraint | Definition |
| --- | --- |
| `questions_pkey` | `PRIMARY KEY (id)` |
| `unique_exam_question` | `UNIQUE (exam, exam_year, section, question_number)` |
| `questions_status_check` | `status = ANY (ARRAY['draft', 'published'])` |
| `valid_correct_option` | `correct_option IS NULL OR correct_option >= 0 AND correct_option <= 3` |
| `valid_options` | `jsonb_typeof(options) = 'array' AND jsonb_array_length(options) = 4` |

Both indexes are unique B-tree indexes: `questions_pkey` on `id`, and `unique_exam_question` on `(exam, exam_year, section, question_number)`. The `id` column is `bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL`.

### RLS, policies, grants, and roles

- RLS is enabled on `public.questions`; `FORCE ROW LEVEL SECURITY` is false.
- Policy **`Public can read published questions`** applies to `anon` and `authenticated` for `SELECT`, with a condition requiring `status = 'published'`.
- Direct table/column grants exist for `anon`, `authenticated`, `service_role`, and `postgres` on `questions`; no grant option was reported for the API roles. These SQL privileges do not bypass RLS.
- No write RLS policies for `anon` or `authenticated` were found.
- `service_role` has the `BYPASSRLS` role attribute. `postgres` also reports `BYPASSRLS`; the audit connection had `current_user = session_user = postgres`. This connection role is not evidence of the deployed FastAPI connection role.

The findings above distinguish SQL grants from RLS policies: a direct SQL grant does not, by itself, establish which operations succeed through RLS.

### Follow-up catalog checks

- `auth.users.id` is `uuid NOT NULL`, matching the Auth foreign-key type in the local Phase 6 role draft. This verifies type compatibility, not migration history or permission to add the foreign key.
- `questions_id_seq` is an identity sequence owned by `public.questions.id`, with `bigint` type, start 1, increment 1, minimum 1, maximum 9223372036854775807, cache 1, and cycling disabled.
- PostgreSQL default ACLs for objects created by `postgres` in `public` grant table privileges to `anon`, `authenticated`, `service_role`, and `postgres`; sequence defaults grant `SELECT`, `UPDATE`, and `USAGE` to those roles. Table defaults include `MAINTAIN` on PostgreSQL 17. `supabase_admin` has a similar broad default table/sequence ACL. Confirm the actual migration executor before relying on either owner's defaults.
- `public.questions` remains the only application table in `public`; the catalog/role names in local drafts do not collide with the current public relations.
- Both `storage.buckets` and `storage.objects` have RLS enabled and `FORCE RLS` false. The catalog query returned no policies for those two relations. Bucket visibility/configuration and any external Storage settings remain unchecked.
- The connection used for this catalog query was PostgreSQL 17.6, database `postgres`, role `postgres`.

## Assumptions and design proposals — not production facts

The architecture and schema documents define a target design. The following are proposals only and must not be read as deployed objects or verified configuration:

- Keep the existing `questions` table and its IDs as the canonical legacy question identity; preserve its current columns and meanings during any future compatibility work.
- Add normalized catalog, profile/role, question revision, media, test/PYQ, attempt/result, bookmark, report, and audit entities in staged migrations.
- Use stable option IDs in revisions while retaining the legacy `options` array and `correct_option` meaning until a validated migration path exists.
- Use Supabase Auth as identity, FastAPI for protected application operations, and database authorization/RLS as an additional security boundary.
- The ER relationships, UUID choices for proposed entities, FK targets, indexes, checks, role model, and policy design in `docs/architecture.md` and `docs/database-schema.md` remain design choices, not observed production schema.
